# DocumentFlow production audit

Audit date: 2026-09-25  
Scope: Gate #5, repository `D:\Projects\HayDev\HayDevOSv1`, linked Supabase project `rljeqbffppqfxkwcptgs`.

## Current document architecture

DocumentFlow is currently a client-only demonstration module. `DocumentFlowView` initializes records, batches, jobs, exports, schemas, and workers from `src/modules/documentflow/data.ts`; timers simulate pipeline transitions and UI actions mutate React state. There are no authenticated DocumentFlow routes and no authoritative persistence path for those UI records.

The production server architecture already used by LeadOS and QuoteFlow is reusable: Next.js route handlers call `withTenantApi`, which resolves the opaque database session, active membership, organization, and role; unsafe requests also receive origin checks. Domain services are server-only and use Prisma through the restricted runtime role.

## Existing database models

`DocumentRecord` and `DocumentField` exist in PostgreSQL. `DocumentRecord` holds organization, filename, browser-supplied MIME-shaped metadata, size, workflow status, uploader, batch, classification, and creation time. It has no storage bucket/key, hash, immutable version, source binding, archive state, current-version pointer, scan state, access events, or generation state.

`GeneratedQuoteDocument` exists from Gate #4. It binds a quote version to a format/template, stores the full reproducible snapshot and a SHA-256 of that JSON snapshot, and is runtime-immutable. `storagePath` is nullable and no binary is generated or stored.

## Existing generators

There is no server PDF or DOCX renderer. QuoteFlow's generate route calls `generateQuoteDocument`, which persists snapshot metadata only. The older visual QuoteFlow and Audit UI files contain toast-only PDF/DOCX buttons. DocumentFlow preview content is synthetic text from `fauxExcerptFor`.

## QuoteFlow integration

QuoteFlow already provides the correct immutable source: `QuoteVersion` contains customer, item, and quote snapshots plus authoritative Decimal totals, terms, locale-neutral data, template version, and timestamps. Composite foreign keys enforce quote/version/tenant consistency. The missing link is a canonical document model, binary renderers, DocumentFlow version metadata, and private Storage persistence.

## LeadOS attachments

LeadOS has no authoritative file attachment model or upload route. Lead activity text may mention attachments, but no bytes are persisted. Gate #5 will expose reusable source binding for `LEAD`; it will not invent an OCR/attachment workflow or migrate nonexistent binary data.

## Temporary/local file usage

No production server path writes business documents to disk. The current UI creates in-memory mock records and simulated progress. No `fs.writeFile` authoritative artifact path was found. The target renderers can return buffers directly and therefore need no repository or OS temporary document files.

## Current file access model

There is no upload/download authorization flow. DocumentFlow has no API; its download/export affordances are inert or mock. Quote document metadata is readable only through tenant-scoped QuoteFlow services, but there is no file to authorize or deliver.

## Current storage paths

No Supabase bucket exists in the linked project and no custom `storage.objects` policies exist. `GeneratedQuoteDocument.storagePath` is empty. The prior architecture document proposes an organization-prefixed immutable key but it is not implemented.

## Existing hashes

Gate #4 computes SHA-256 over serialized quote snapshot metadata. It does not hash generated bytes. Session tokens use separate SHA-256 digests. Gate #5 must hash the actual uploaded/generated bytes and store that hash on an immutable document version.

## Existing templates

`QuoteSettings.documentTemplateVersion` and `QuoteVersion.templateVersion` preserve a string such as `quote-v1`, but there is no template identity/version record, RBAC administration, or renderer binding. Visual template data in old mock modules is not authoritative.

## Existing MIME validation

The browser-only upload dialog compares browser MIME strings and extensions. It accepts PDF, DOCX, XLSX, CSV, TXT, PNG, and JPEG, but performs no server validation or signature inspection. Browser MIME is therefore not a security control.

## Existing upload limits

The UI displays 25 MB per file, but no server route enforces body size, file count, part count, or file size. Supabase has no bucket-level limit because the bucket does not yet exist.

## Existing Owner AI document access

Owner AI's production route connects LeadOS and QuoteFlow reads to canonical services. Document summaries and document search still fall through to development-only mock tools and fail closed in production. There is no production document read/generate/archive tool and no direct Storage access, which is the safe starting state.

## Security risks

- Client-only MIME/size checks are bypassable.
- No authoritative binary/hash pair or immutable file history exists.
- Mock DocumentFlow records and simulated successful uploads can misrepresent production state.
- A future direct Storage URL/path implementation could bypass HayDevOS sessions and RBAC.
- `DocumentRecord` cannot currently prove that its uploader or source belongs to the same tenant beyond the existing uploader membership trigger.
- No malware-scanner state or quarantine extension point exists.

## Tenant risks

- Current UI uses a fixed demonstration organization and uploader.
- No server-side document list/detail/download query applies the active organization.
- No database invariant checks a generic document source against the source entity's organization.
- A client-supplied object path would currently have no canonicalization or ownership verification.

## Data-loss risks

- UI records disappear on refresh/restart.
- PostgreSQL metadata and Storage objects have no two-phase/compensation protocol.
- Database backup alone would not preserve Storage objects.
- There is no DB-to-object/object-to-DB reconciliation report.
- Historical files could be overwritten if future uploads reused a key.

## Reusable components

- Opaque session, active-tenant resolution, same-origin mutation guard, structured API errors, and Zod request validation.
- Restricted `haydev_runtime` role, RLS/grant migration pattern, membership triggers, immutable-history triggers, and audit log.
- `QuoteVersion` customer/item/quote snapshots and Decimal totals.
- QuoteFlow/Owner AI domain context and canonical service patterns.
- Existing DocumentFlow visual shell, document tables, viewer, and upload dialog styling.

## Required schema changes

- Extend `DocumentRecord` into the logical document aggregate while preserving legacy fields for compatibility.
- Add immutable `DocumentVersion` rows containing bucket, key, server filename, detected MIME, byte size, byte SHA-256, scan state, source snapshot, template version, locale, creator, status, and failure metadata.
- Add `DocumentGeneration`, `DocumentTemplate`, and append-only `DocumentAccessEvent`.
- Bind `GeneratedQuoteDocument` to both logical document and immutable document version and add locale.
- Add tenant composite keys, source-tenant trigger checks, current-version consistency, membership triggers, constrained state transitions, RLS, least-privilege grants, and append-only history.

## Required storage changes

- One private `haydev-documents` bucket with a 25 MB bucket limit and an explicit MIME allowlist.
- Server-only Supabase secret in a narrow adapter; no browser key or direct upload.
- Canonical immutable keys under `organizations/{orgId}/documents/{documentId}/versions/{versionId}/{safeFilename}`.
- `upsert: false`; new version means a new key.
- Short-lived signed downloads created only after HayDevOS session, tenant, RBAC, ownership, and scan/status checks.
- No permissive browser Storage policies; HayDevOS custom auth remains the authorization boundary.

## Migration plan

1. Add and locally validate the Prisma migration and generated client.
2. Introduce the server-only Storage adapter and environment contract.
3. Implement upload validation, pending/finalized version lifecycle, compensation, audit, list/detail/archive/download, and reconciliation.
4. Build one immutable QuoteVersion document model and server renderers for JSON, PDF, and DOCX.
5. Route QuoteFlow and Owner AI through DocumentService and replace production DocumentFlow mock state with authenticated APIs.
6. Configure and verify the private Supabase bucket through the Storage API.
7. Apply the exact migration to the linked project, record its checksum in the Prisma ledger, verify schema/RLS/grants/triggers/storage policies, run advisors, and compare schema drift.
8. Run security, concurrency, persistence, Unicode, renderer consistency, existing Gates #1-4, lint, typecheck, build, and dependency audits.
